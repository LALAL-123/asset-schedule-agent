# 05 复盘

> 初稿，按本人实际体会修改。

## 最难的问题

**让“确认边界”不依赖模型自觉。** 提示词可以写“硬性时间不得改、只能存草稿”，但模型可能把替代时段直接当成已确认，或在保存失败后仍写“已保存”。最后的做法是三层：提示词约定规则；`save_draft` 服务端复核审核结论、占用和硬性时间；`finish` 之后由护栏用工具记录核对结论并重算 `task_status`。模型负责选动作，结论里的事实由工具决定。

**重复提交的定义。** 若按“草稿内容哈希”去重，用户确认替代时段后内容会变，同一请求就会产生两份草稿。因此按 `request_id` 建键：内容相同去重，内容变化升版本，存储里始终只有一份。幂等键由系统注入，不让模型传，避免模型改写导致去重失效。

**检查不能绑定执行路径。** 真实模型可能先查时段再查规则，也可能多查一次。验收检查只看最终结果、工具调用事实和存储，不比对步骤顺序，Mock 和真实模型共用同一套检查。

## 学习收获

- ReAct 的价值在“观察改变动作”，所以用例要成对设计：同一请求只改一个工具结果（占用时段、授权状态），看动作是否跟着变。
- 工具返回要给足决策信息（如 `free_slots_nearby`、`occupied_by`），但不替模型做决定。
- 把“为什么这样做”做成工具的必填参数 `decision_note`，比要求模型输出思维过程更稳定，也更容易审计。
- 真实模型的失败不全是模型的错：第 2 轮分数下降，读 Trace 才发现是合成数据自相矛盾（素材写“已核验”，授权库查不到）；第 3 轮又发现护栏自己把“有空闲但没选”写成了 no_free_slot。护栏同样要按事实测试。

## 下一步

1. GLM-4-Flash 三轮的主要错误是保存失败后不改时段、不肯选建议时段。下一步把这两种情况改为退回 finish，并让 `query_slots` 返回推荐时段；再换更强的模型复测。
2. 支持跨日替代和渠道频控（同渠道相邻两条间隔），把排期从“找空位”升级为带约束的分配。
3. 草稿存储换成带乐观锁的数据库，覆盖并发提交同一请求。
4. 把 `user_confirmations` 做成真正的多轮会话：Agent 输出确认问题，用户回复后续跑。
